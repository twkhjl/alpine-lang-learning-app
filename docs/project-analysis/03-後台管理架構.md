# 後台管理架構

## 後台頁面組成

目前後台不是單頁式應用，而是由多個 HTML 頁面組成：

- `admin-login.html`
- `admin-dashboard.html`
- `admin-words.html`
- `admin-word-edit.html`
- `admin-assets.html`
- `admin-tags.html`

這些頁面共用：

- `public/assets/css/admin.css`
- `public/assets/js/admin-shell.js`
- `public/assets/js/admin-auth.js`
- `public/assets/js/admin-api.js`
- `public/assets/js/admin-i18n.js`

另外每頁各自對應自己的 controller：

- `admin-dashboard.js`
- `admin-words.js`
- `admin-word-edit.js`
- `admin-assets.js`
- `admin-tags.js`
- `admin-login.js`

---

## 後台架構特性

### 1. 多頁 HTML 而不是單一 SPA

每次切到不同後台頁面，本質上都是整頁重載。

優點：

- HTML 結構直觀
- 各頁邏輯相對隔離
- 不需要前端 router

缺點：

- 共用狀態管理較弱
- 每頁都要重新做 auth guard 與初始化
- 一致性很容易漂移

### 2. 有共用 shell，但各頁仍各自啟動

`admin-shell.js` 目前負責：

- 定義後台 routes
- 共用 sidebar 渲染
- 根據目前頁面設定 active nav
- 套用頁面標題
- 配合 `admin-i18n.js` 重繪文案

這代表後台已從「每頁各寫一份選單」進一步整理成共用導航來源。

---

## Sidebar 與頁面識別

`admin-shell.js` 中定義了 `ADMIN_ROUTES`，其中重要欄位包括：

- `path`
- `navKey`
- `icon`
- `titleKey`
- `visibleInSidebar`

目前 visible 的主要頁面是：

- dashboard
- words
- assets
- tags

特別值得注意的是：

- `admin-word-edit.html` 雖然是合法 route
- 但 `visibleInSidebar: false`

這代表 `Edit Word` 是流程頁，不是主選單頁。正確進入方式是從 words 清單點進去，而不是直接固定掛在主選單上。

---

## 後台登入與守門

後台的第一層守門在 `admin-auth.js`。

它負責：

- 建立 admin 專用 Supabase client
- 呼叫登入 API
- 將 session 寫入 Supabase client
- 驗證目前登入使用者是否存在於 `admin_users`
- 未登入或未授權時導回 `admin-login.html`

這裡的權限模型不是只看「是否登入」，而是要同時滿足：

1. 有有效 session
2. 該 session 的 `user_id` 存在於 `admin_users`

---

## 後台資料存取分工

後台的讀取與寫入不是完全同一路。

### 讀取

很多讀取流程可以直接從瀏覽器讀 Supabase：

- dashboard summary
- words list
- word detail
- tag list
- asset references

這些通常經由 `admin-api.js` 封裝。

### 寫入

受保護寫入不直接從瀏覽器打資料表，而是透過 Worker：

- create word
- update word
- create tag
- update tag
- delete tag

這樣做的主要目的：

- 避免把 service role 暴露在前端
- 用 Worker 控制 CORS、session 驗證與錯誤格式
- 讓 DB 寫入集中在 RPC 與 server-side contract

---

## `admin-api.js` 的角色

`admin-api.js` 是後台資料層的總入口。它同時做幾件事：

- 建立或取得 admin Supabase client
- 正規化 words / tags / assets / dashboard 資料
- 定義前台 controller 可直接用的讀取函式
- 封裝需要走 Worker 的寫入函式

幾個重要函式包括：

- `createWord`
- `updateWord`
- `createTag`
- `updateTag`
- `deleteTag`
- `loadWordList`
- `loadWordDetail`
- `loadTagList`
- `loadAssetReferences`
- `loadDashboardSummary`

這個檔案是後台 controller 與資料來源之間的邊界層，重要性很高。

---

## Dashboard 頁面

`admin-dashboard.html` + `admin-dashboard.js` 提供的是「管理總覽」，不是操作頁。

目前功能重點：

- 顯示字詞總數
- 顯示標籤總數
- 顯示缺少圖片的字詞數
- 顯示缺少音檔的字詞數
- 顯示最近更新字詞
- 顯示系統狀態文案

這個頁面是典型 read-only 聚合頁。

---

## Words 清單頁

`admin-words.html` + `admin-words.js` 是後台最主要的操作入口之一。

目前主要責任：

- 搜尋字詞
- 依 tag 篩選
- 依有無圖片篩選
- 依有無音檔篩選
- 分頁
- 導向字詞建立 / 編輯頁

這個頁面扮演的是索引頁，不直接編輯內容本身，而是把使用者送到 `admin-word-edit.html`。

---

## Word 編輯頁

`admin-word-edit.html` + `admin-word-edit.js` 處理兩種模式：

- create
- edit

依照目前的修正後行為：

- 合法 `id` 才進 edit
- 無效 `id` 不會默默 fallback 成 create

這個細節很重要，因為它避免了「本來要編輯某筆資料，結果因為 URL 壞掉而誤新增新資料」。

頁面可維護內容包括：

- `image_url`
- `zh-TW` 文字
- `id` 文字
- `en` 文字
- 各語言 pronunciation
- 各語言 audio filename
- tags 關聯

實際寫入是透過 Worker + RPC。

---

## Tags 頁

`admin-tags.html` + `admin-tags.js` 提供基本標籤 CRUD。

目前功能重點：

- 顯示 tags 清單
- 開 modal 新增 tag
- 開 modal 編輯 tag
- 刪除未被使用的 tag
- 阻止刪除仍被 `word_tags` 引用的 tag

這頁的資料關鍵是：

- 主表 `tags`
- 翻譯表 `tag_translations`
- 使用量來自 `word_tags`

需要注意的設計點：

- tag 本身不是單一語言名稱，而是多語名稱集合
- 刪除 tag 時要先檢查 usage count

---

## Assets 頁

`admin-assets.html` + `admin-assets.js` 目前不是完整媒體管理器，而是「媒體引用檢視器」。

目前已知用途：

- 檢視資料庫中 image/audio stored path
- 搜尋 path
- 依類型篩選 image / audio
- 依語言篩選 audio
- 看有哪些字詞引用某個媒體

這個頁面很實用，但範圍要說清楚：

- 它不是 R2 物件瀏覽器
- 目前不提供上傳
- 目前不提供刪除
- 它顯示的是資料庫記錄的引用，而不是實際檔案存活狀態

---

## Login 頁

`admin-login.html` + `admin-login.js` 專注於：

- 收帳密
- 顯示登入狀態
- 呼叫 username/password login API
- 成功後導向 dashboard

這裡不是直接拿 email/password 跟 Supabase Auth 互動，而是先透過 Worker 走「admin username -> account -> auth session」的流程。

---

## 後台多語系

目前後台已引入 `admin-i18n.js`，支援：

- `zh-TW`
- `en`

做法是：

- 字串 key 集中在字典
- shell 與各頁 controller 使用 translator
- sidebar 語系切換觸發重新套字

這比原本把字串直接寫死在每頁 HTML 好很多，但目前仍有兩個現實問題：

1. 某些中文字串有編碼污染痕跡
2. 文案仍偏散，還沒完全資料化到 DB 層

---

## 後台目前的優點與限制

### 優點

- 分頁邏輯清楚
- auth guard 已存在
- CRUD 主流程已通
- 共用 shell 與 i18n 已成形

### 限制

- 每頁仍偏手工 controller
- 表單驗證與錯誤狀態管理還不夠系統化
- 寫入錯誤多半仰賴 Worker 與 DB 回應，前端層的 UX 尚可再加強
- 完整媒體管理尚未實作

---

## 適合的後續演進方向

1. 把 admin controller 的共同模式抽成 helper
   - loading
   - error
   - success message
   - empty state

2. 將後台文案繼續清理
   - 尤其是中文編碼問題

3. 為表單類頁面建立更清楚的驗證層

4. 補上更完整的手動測試腳本或 E2E

5. 如果功能再繼續成長，再評估是否要把後台改成單一前端應用
