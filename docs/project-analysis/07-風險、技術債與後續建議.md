# 風險、技術債與後續建議

## 這份章節的目的

前面幾份文件是在描述「現在專案如何運作」；這一份則是直接指出：

- 哪些地方目前有風險
- 哪些問題會在未來擴充時放大
- 哪些事情值得排進下一輪工作

---

## 風險一：前台核心邏輯過度集中在 `main.js`

### 現象

- `main.js` 已超過千行
- 前台狀態、事件、翻譯、偏好、卡片、清單、音訊都在同一檔

### 風險

- 任一小修改都容易影響其他流程
- 心智負擔高
- 測試定位成本變高
- 新人接手時很難快速切出責任邊界

### 建議

- 先做邏輯拆分，不一定要一次轉框架
- 可先分成：
  - data loader
  - preferences
  - view state
  - audio
  - i18n

---

## 風險二：編碼與文案品質不一致

### 現象

- `seed.sql` 可見明顯中文亂碼
- `admin-i18n.js` 的部分繁中文字串看起來也有編碼污染跡象
- 過往 admin HTML 曾出現亂碼與壞 markup 問題

### 風險

- UI 可讀性不穩定
- 匯入 / 匯出資料時容易放大污染
- 很難判斷問題是資料庫、檔案編碼還是終端顯示

### 建議

1. 明確統一 UTF-8 編碼
2. 製作資料健診腳本，找出異常字元
3. 重新整理 seed 來源，不要再用污染後內容當權威版本

---

## 風險三：後台雖已成形，但還是偏早期 CMS

### 現象

- 已有 dashboard / words / tags / assets
- 但 assets 仍是引用檢視，不是完整媒體管理
- 缺少 bulk import/export、審計、變更歷程等更成熟能力

### 風險

- 功能越加越多時，現有頁面 controller 會開始失控
- 使用者可能誤以為 assets 頁能直接管理檔案

### 建議

- 先明確定義後台 scope
- 將「已支援 / 未支援」寫進介面或文件
- 若要變成完整 CMS，再規劃第二階段

---

## 風險四：前端、Worker、DB contract 高度耦合

### 現象

- `admin-api.js`
- `admin-auth-worker.js`
- Supabase RPC / view

三者必須維持一致。

### 風險

- 任一邊改名或改欄位，其他兩邊就可能壞
- 很容易出現「本地 test 過，但遠端整合壞」的狀況

### 建議

1. 把 contract 文件化
2. 對主要 endpoint 做 smoke test
3. 對 migration / deploy / test 做固定流程

---

## 風險五：部署與資料遷移同步性不足時，錯誤會很隱晦

### 已發生的典型例子

- Worker 線上版本落後，導致 admin route 404
- identity sequence 未同步，導致 tag create 500

### 問題本質

這不是單純程式碼 bug，而是：

- 部署版本
- DB migration
- 遠端資料狀態

沒有同步造成的整合錯誤。

### 建議

建立固定 checklist：

1. 改到 Worker 先 deploy
2. 改到 migration 先 push
3. push 後驗證主要 preflight 與 CRUD endpoint

---

## 風險六：後台多語系已開始導入，但治理尚未完成

### 現象

- 後台已有 `admin-i18n.js`
- 目前支援 `zh-TW` 與 `en`
- 但後台文案仍屬程式內字典，尚未資料化

### 風險

- 文案更新仍要改程式碼
- 中英一致性靠人工維護
- 若未來要支援更多語言，成本會快速上升

### 建議

如果後台多語系會長期發展，可評估兩條路：

1. 維持程式內字典，但建立更清楚的 key 命名與檢查機制
2. 將後台 UI 翻譯也逐步資料化

---

## 建議的近期優先順序

### 第一優先：穩定性

- 清理編碼問題
- 補整合 smoke test
- 強化部署與 migration checklist

### 第二優先：可維護性

- 拆 `main.js`
- 抽共用 admin controller helper
- 梳理 view / RPC contract

### 第三優先：功能完整度

- 完善 assets 管理
- 補 import/export
- 補操作紀錄或審計資訊

---

## 建議的中期重構藍圖

### 選項 A：維持目前技術棧但做模組化

適合情境：

- 團隊偏小
- 需求成長中等
- 希望維持部署輕量

重點：

- 不推翻 Alpine
- 先提升檔案結構與測試完整度

### 選項 B：後台逐步產品化

適合情境：

- 後台功能會快速增加
- 會有更多管理流程、審批或批次操作

重點：

- 可能需要更完整的前端架構
- 可能需要更正式的 API contract 與權限模型

---

## 最後結論

這個專案目前已經不是單純 demo，而是有實際資料模型、登入流程、後台 CRUD 與測試基礎的可運作系統。  
但它同時也還保留典型的成長期特徵：

- 核心邏輯集中
- 文件不足
- 編碼與資料品質不一
- 部署與資料遷移同步需要人工把關

如果接下來要讓它更穩定、更容易交接，最值得投資的事情不是立刻加更多功能，而是：

- 整理資料品質
- 強化契約與測試
- 把主流程文件化

這也是本資料夾存在的目的。
