# 部署設定與維運手冊

## 這份文件的定位

這不是完整的 DevOps 手冊，而是給接手開發者或維運者的實務操作指南。  
重點是回答三個問題：

- 本地怎麼跑
- 線上哪幾層要同步
- 出錯時先查哪裡

---

## 主要環境構成

目前專案至少包含三個實際運行層：

1. 靜態前端頁面
   - 可由 Live Server、HTTP server 或 GitHub Pages 提供
2. Cloudflare Worker
   - 提供 admin login 與 protected admin API
3. Supabase
   - 提供 Auth、Database、REST、RPC

任何後台功能異常，都要把這三層一起看。

---

## 本地開發基本方式

### 前台 / 後台靜態頁面

最簡單方式：

```bash
python -m http.server 3000
```

或使用 Live Server。

常見本地網址：

- `http://127.0.0.1:5500/index.html`
- `http://127.0.0.1:5500/admin-login.html`

注意：

- 不要用 `file://`
- 一定要用 HTTP origin，否則 auth 與 fetch 行為會失真

---

## 前端連線設定

`public/assets/js/supabase-config.js` 是本地與部署環境都會吃到的設定入口。

目前可見欄位：

- `url`
- `publishableKey`
- `adminAuthApiUrl`

重點：

- `adminAuthApiUrl` 可由 `window.LEXICON_ADMIN_AUTH_API_URL` 覆蓋
- 若未覆蓋，會預設指向已部署的 Worker

---

## Worker 部署設定

`wrangler.jsonc` 目前重點：

- `name`: `alpine-lang-learning-app-admin-auth`
- `main`: `workers/admin-auth-worker.js`
- `compatibility_date`: `2026-04-25`
- `vars.SUPABASE_URL`
- `vars.ADMIN_API_BASE_PATH`
- `vars.ADMIN_ALLOWED_ORIGIN`

目前 `ADMIN_ALLOWED_ORIGIN` 至少包含：

- `http://127.0.0.1:5500`
- `https://twkhjl.github.io`

這表示本地 Live Server 與 GitHub Pages 都應能打到 Worker。

## 後台功能變更時的同步原則

### 如果只改前台 UI

通常需要：

- 改 HTML / CSS / JS
- 不一定需要 deploy Worker
- 不一定需要 push migration

### 如果改後台讀取邏輯

通常需要：

- 改 `admin-api.js` 或對應 controller
- 視情況改 view 或 query
- 若不涉及 Worker route，可不 deploy Worker

### 如果改後台寫入邏輯

通常需要三步都做：

1. 改前端 payload / UI
2. 改 Worker handler 或 route
3. 改 Supabase migration / RPC

少做任一層都容易壞。

---

## 建議的變更後操作順序

### 改到 migration 時

1. 先檢查 migration SQL
2. 套用到目標 Supabase
3. 驗證 migration list

### 改到 Worker 時

1. 本地測試 Worker unit test
2. deploy Worker
3. 驗證 `OPTIONS` 與主要 endpoint

### 改到後台頁面時

1. 本地開頁面
2. 手動測 UI 流程
3. 若依賴遠端 Worker，確認 CORS 正常

## 常見故障與排查順序

### 症狀：登入失敗

先查：

1. `admin-login.html` 是否載入最新 JS
2. `adminAuthApiUrl` 是否正確
3. Worker `/api/admin/auth/login` 是否正常
4. `admin_accounts` 是否有對應 username
5. `admin_users` 是否有授權

### 症狀：後台頁面一開就被導回 login

先查：

1. Supabase session 是否存在
2. `admin-auth.js` 是否成功 `setSession`
3. `admin_users` 是否存在該 user

### 症狀：新增 / 修改標籤或字詞時 CORS 錯誤

先查：

1. `ADMIN_ALLOWED_ORIGIN` 是否包含當前 origin
2. Worker 是否已部署新版本
3. `OPTIONS` preflight 是否回 `204`

### 症狀：新增 / 修改時 404

先查：

1. 前端打的 endpoint path 是否正確
2. 線上 Worker 是否包含該 route
3. `ADMIN_API_BASE_PATH` 是否與前端預期一致

### 症狀：新增 / 修改時 500

先查：

1. Worker 回傳的 `message/details`
2. RPC 是否存在
3. migration 是否已套用
4. sequence / identity 是否同步

## 與資料遷移相關的實務提醒

這個專案已經出現過典型 sequence 問題：

- table 改成 identity
- 既有資料仍沿用舊 id
- sequence 沒調整到 `max(id)`
- 下一次 insert 直接主鍵衝突

因此如果你再做類似 migration：

- 不要只改欄位定義
- 要一起考慮 `setval()`

## 建議保留的固定維運清單

每次部署後台相關功能後，至少做一次：

1. `npm test`
2. 本地登入一次
3. 開 `admin-dashboard.html`
4. 開 `admin-tags.html` 測新增 / 修改 / 刪除
5. 若有改字詞寫入，再測 `admin-word-edit.html`
6. 驗證 Worker `OPTIONS` 與主要 CRUD endpoint
